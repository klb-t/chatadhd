# External resources: reversible implementation decision, B, 2026-10-09

Owner clarification extends R15/R20/R21; this document is an implementation boundary, not a new owner requirement or a claim that the complete clarification is implemented.

The first slice composes existing Catalog locator access (file / ZIP member / byte slice / JSON pointer), hash verification, the lossless export-3 provider parsers, and the existing Database nodes/links. `Catalog::read_resource(unit_id)` is shared by catalog preview (the existing workbench renderer) and the registered `catalog.read_resource` TaskEngine handler. There is no renderer-specific parser or second method/configuration engine.

Conversation nodes preserve provider graph metadata; message nodes preserve role, status, alternative branches and verbatim provider fields. Parent and containment edges are queryable through existing Database graph APIs. IDs pin content and mapping version. A transaction commits the projection and its last-successful root snapshot together. Failed source reads return `current=false`, an exact error, and any retained snapshot. They never clear it or implicitly authorize using stale context. Task completion means inspection completed; consumers must inspect current/status before use.

This slice is readonly, on-demand, version-pinned, with a persisted derived graph snapshot. These are disclosed implemented choices, not new coupled policy requirements. Alternatives (eager materialization, live source tracking, cache/index controls, overlay, write-back and combined embed/reference) remain unimplemented and need separately validated policy data. Existing Catalog copy/link settings remain unchanged. The linked conversation placeholder is not yet transparently resolved by ordinary chat's get_messages path.

Unknown JSON domains have uncertain mapping and explicit `coverage=not_implemented`; the locator and content hash remain available. Their unclassified payload is not inserted into an exportable graph (it may contain credentials). Unknown conversation fields remain preserved by the existing provider interpretation. No remote transport, model discovery, automatic adapter activation, private-data egress or credential handling is added. Source availability does not expand authorization.

Next: project accepted external RuntimeProfile overlays with their existing strict validator, graph-visible effective fields/hash and a real Runtime consumer; preserve rejected/unknown mapping without activating it. Then express adapter declaration, implementation, tests/evidence, permission and discovery workflow through the existing loom.method_graph/1 and loom.method_run_trace/1 contracts. Nested archives already exist in the lossless importer but are not yet a composed catalog reference selector. Full cross-resource context/analysis integration and generic discovery are open.

## Second slice: existing external profile binding

Accepted `loom.runtime_profile_overlay/1` resources compose RuntimeProfile::builtin + with_overlay, exactly the existing resolver/validator. Their effective values are recursively projected as profile_field nodes with escaped RFC 6901 pointers. Hashes match the real Runtime consumer when the owner already bound that same file through `<data>/profiles/<domain>.pack` (the test uses an explicit symlink to the synthetic external file). Reading a catalog resource does not install or select that profile. A missing symlink target already fails through the existing RuntimeProfile loader; no new fallback or configuration engine was added.

Invalid/unknown overlay fields preserve exact source bytes and produce uncertain mapping plus the validator error. They are not silently discarded, activated or copied as unclassified values into an exportable graph. Rejected profile overlays additionally expose their JSON syntax tree as external:json_field nodes, including unknown keys and RFC 6901 selectors. Unclassified scalar values remain hash-pinned value_ref references to the exact source rather than plaintext in graph exports. Runtime interpretation, credential_ref materialization and separate permission/evidence nodes remain pending. Available source bytes do not imply a usable domain mapping. Source observation is persisted separately as root metadata `availability`; last-successful projections keep their identity across source failure and reopen. This also applies to the first-slice conversations.

Evidence uses both conversations in the synthetic ZIP, compares copy/reference graph packets and provider graph/status/raw messages against the real lossless importer, then confirms keyboard selection through the actual Chromium workbench/server endpoint. Runtime profile evidence confirms a graph-visible pattern changes actual analyzer output, explicit pause/resume of the TaskEngine inspection, unavailable-reference startup rejection, repair/reopen and zero HTTP requests on the injected transport. This does not establish generic discovery or ordinary-chat transparent reference hydration.

## R42 projection vocabulary

The node-kind and relation-name choices are canonical data in `loom/data/runtime/resource_projection.pack`. Runtime uses the existing strict RuntimeProfile loader; its compiled fallback is generated only by `gen_runtime_profiles.py`. The exact effective descriptor/hash is captured in each resource snapshot and graph IDs, so vocabulary updates produce a separate projection rather than reinterpreting immutable rows. Unknown JSON structural fields also use this descriptor. Tests change message kind/parent predicate solely through an overlay, retain identical conversation data/analyzer identity, reject an empty or removed mandatory kind and retain the preceding graph on error.

Remaining literals have exact R42 roles: schema/JSON lookup keys are contract names (1); ID prefixes delimit the serialized graph identity (4); source/mapping lifecycle states and `catalog.read_resource` are mechanism vocabulary (3); validation diagnostics are developer diagnostics (6). No user-facing strings, prompts, model choices, privacy/budget caps or configurable type-name lists were added to product code. No broad allowlist was created or changed. The first conversation commit preceded this descriptor; the data-driven descriptor supersedes its vocabulary implementation without deleting history.
