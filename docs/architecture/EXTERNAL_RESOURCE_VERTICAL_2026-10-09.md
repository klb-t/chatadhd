# External resources: reversible implementation decision, B, 2026-10-09

Owner clarification extends R15/R20/R21; this document is an implementation boundary, not a new owner requirement or a claim that the complete clarification is implemented.


## Current candidate integration (B continuation)

The sections below retain the sequence of earlier slices. Current implemented choices supersede their historical next steps: the public DB-free `loom.export_mapping/1` hook is shared with D; catalog copy uses the existing full provider model writer; reads have independent `resource_read` data for `projection_storage=snapshot|transient` and `content_index=sketch|none`. Defaults remain snapshot/sketch. An opt-in transient+none path creates no durable derived conversation payload in a fresh store. The tests inspect SQLite/WAL, blobs, logs and temporary-file creation/removal, not only exported JSON. An existing content index or snapshot is retained as history; selecting none does not promise to erase it. Scan still reads the container as required by its adapter. Read scope measures unit bytes; container I/O is explicitly not instrumented.

The index-retention contract `catalog.index_retention/1` makes the migration explicit: none→sketch restores the previously withheld fields, while sketch→none cannot certify removal of prior payload. Legacy none rows without that evidence report unknown retention history; current empty fields do not prove old WAL contents. Rejected or partially completed scans keep their checkpoints incomplete, including forced reads with an unchanged fingerprint. Successful units and historical snapshots remain intact for retry. An explicit new store can establish no-index history; this is not automatic deletion or a policy change.

`Catalog::execute_resource` resolves its descriptor through existing MethodRegistry and records `loom.method_graph/1` / `loom.method_run_trace/1` using the real GraphPacketStore. The result records source/hash/selector, parser and mapping versions, original source-array ordinal (or explicit unit-relative scope for old rows), exact effective configuration, observed status/coverage, available validation and produced_by. A shared outer transaction commits snapshot and receipt together. Missing implementation is unavailable; a denied host read returns Auth before source access, dispatch or storage writes. A declaration cannot grant an executor. The existing authenticated task-submission boundary is the caller's local-read authority; it grants no model egress. This is not a new ACL engine or a claim to have audited all application authentication.

Transient TaskEngine results contain only a reference, method metadata and receipt, rather than persisting the in-memory projection through set_result. Direct read/view can inspect transient content in memory. New resource receipts default to `implicit_context_eligible=false` from the method descriptor. The existing implicit context resolver, ordinary runtime knowledge context and latest-run C API share a store filter before LIMIT. Historical runs without the field retain prior behavior; explicit run inspection remains available. Opt-in eligibility still grants no source disclosure permission.

Source changes/unavailability produce explicit noncurrent results; any retained snapshot has separate historical identity. Projection descriptor revision 3 retains the full mapper DTO; the earlier revision 2 and catalog source-index fingerprint introduced observed source indices. These versioned interpretations do not rewrite old traces. Existing already imported copies remain unchanged; new copies preserve parents, alternatives, status, groups, attachments and unknown raw fields via the same provider parser. Legacy rows without source_index use unit-relative mapping rather than inventing an original index.

P4a resolves ordinary linked history through the additive Runtime/C ABI ConversationView and the actual ChatView. Legacy storage-only getters deliberately retain the placeholder and perform no source I/O. Open P4b: source→ContextEngine→ordinary chat/headless analysis with separate egress authorization. That integration must use existing R40 privacy decisions before model dispatch and keep full payload out of chat context_trace/storage in the transient variant. Remote/nested reference access, generic discovery, unclassified credential interpretation, live/write-back policy and ExperimentSpec/adoption remain separate work. D's permissive standalone defaults are not installed as product permissions. E's actual graph pane uses existing native profile resolution but is currently a KnowledgeStore consumer, not a Catalog source renderer.

Reversible choices: a DB-free view of existing parsers instead of a second parser or temp DB; native additive pack installation instead of round-tripping old integer values through JavaScript; explicit metadata receipts excluded from implicit context instead of allowing new read history to silently change chat context. These are implementation choices, not new owner requirements.

## Historical first slice

The first slice composes existing Catalog locator access (file / ZIP member / byte slice / JSON pointer), hash verification, the lossless export-3 provider parsers, and the existing Database nodes/links. `Catalog::read_resource(unit_id)` is shared by catalog preview (the existing workbench renderer) and the registered `catalog.read_resource` TaskEngine handler. There is no renderer-specific parser or second method/configuration engine.

Conversation nodes preserve provider graph metadata; message nodes preserve role, status, alternative branches and verbatim provider fields. Parent and containment edges are queryable through existing Database graph APIs. IDs pin content and mapping version. A transaction commits the projection and its last-successful root snapshot together. Failed source reads return `current=false`, an exact error, and any retained snapshot. They never clear it or implicitly authorize using stale context. Task completion means inspection completed; consumers must inspect current/status before use.

This slice is readonly, on-demand, version-pinned, with a persisted derived graph snapshot. These are disclosed implemented choices, not new coupled policy requirements. Alternatives (eager materialization, live source tracking, cache/index controls, overlay, write-back and combined embed/reference) remain unimplemented and need separately validated policy data. Existing Catalog copy/link settings remain unchanged. The linked conversation placeholder is not yet transparently resolved by ordinary chat's get_messages path.

Unknown JSON domains have uncertain mapping and explicit `coverage=not_implemented`; the locator and content hash remain available. Their unclassified payload is not inserted into an exportable graph (it may contain credentials). Unknown conversation fields remain preserved by the existing provider interpretation. No remote transport, model discovery, automatic adapter activation, private-data egress or credential handling is added. Source availability does not expand authorization.

Next: project accepted external RuntimeProfile overlays with their existing strict validator, graph-visible effective fields/hash and a real Runtime consumer; preserve rejected/unknown mapping without activating it. Then express adapter declaration, implementation, tests/evidence, permission and discovery workflow through the existing loom.method_graph/1 and loom.method_run_trace/1 contracts. Nested archives already exist in the lossless importer but are not yet a composed catalog reference selector. Full cross-resource context/analysis integration and generic discovery are open.

## Second slice: existing external profile binding

Accepted `loom.runtime_profile_overlay/1` resources compose RuntimeProfile::builtin + with_overlay, exactly the existing resolver/validator. Their effective values are recursively projected as profile_field nodes with escaped RFC 6901 pointers. Hashes match the real Runtime consumer when the owner already bound that same file through `<data>/profiles/<domain>.pack` (the test uses an explicit symlink to the synthetic external file). Reading a catalog resource does not install or select that profile. A missing symlink target already fails through the existing RuntimeProfile loader; no new fallback or configuration engine was added.

Invalid/unknown overlay fields preserve exact source bytes and produce uncertain mapping plus the validator error. They are not silently discarded, activated or copied as unclassified values into an exportable graph. Rejected profile overlays additionally expose their JSON syntax tree as external:json_field nodes, including unknown keys and RFC 6901 selectors. Unclassified scalar values remain hash-pinned value_ref references to the exact source rather than plaintext in graph exports. Runtime interpretation, credential_ref materialization and separate permission/evidence nodes remain pending. Available source bytes do not imply a usable domain mapping. Source observation is persisted separately as root metadata `availability`; last-successful projections keep their identity across source failure and reopen. This also applies to the first-slice conversations.

Evidence uses both conversations in the synthetic ZIP, compares copy/reference graph packets and provider graph/status/raw messages against the real lossless importer, then confirms keyboard selection through the actual Chromium workbench/server endpoint. Runtime profile evidence confirms a graph-visible pattern changes actual analyzer output, explicit pause/resume of the TaskEngine inspection, unavailable-reference startup rejection, repair/reopen and zero HTTP requests on the injected transport. This does not establish generic discovery or ordinary-chat transparent reference hydration.

## R42 projection vocabulary

The node-kind and relation-name choices are canonical data in `loom/data/runtime/resource_projection.pack`. Runtime uses the existing strict RuntimeProfile loader; its compiled fallback is generated only by `gen_runtime_profiles.py`. The exact effective descriptor/hash is captured in each resource snapshot and graph IDs, so vocabulary updates produce a separate projection rather than reinterpreting immutable rows. Unknown JSON structural fields also use this descriptor. Tests change message kind/parent predicate solely through an overlay, retain identical conversation data/analyzer identity, reject an empty or removed mandatory kind and retain the preceding graph on error.

Remaining literals have exact R42 roles: schema/JSON lookup keys are contract names (1); ID prefixes delimit the serialized graph identity (4); source/mapping lifecycle states and `catalog.read_resource` are mechanism vocabulary (3); validation diagnostics are developer diagnostics (6). No user-facing strings, prompts, model choices, privacy/budget caps or configurable type-name lists were added to product code. No broad allowlist was created or changed. The first conversation commit preceded this descriptor; the data-driven descriptor supersedes its vocabulary implementation without deleting history.


## Historical proposed ordinary-conversation boundary (superseded by the candidate below)

The current public synthetic probe distinguishes full copy (2 conversations,4 messages,2 parent links) from ordinary link (2 placeholders,0 parents). A future additive Runtime ConversationView must join the catalog import journal and actual link provenance; raw_blob emptiness or editable message metadata alone does not prove a link binding. Source changes and unavailable reads require an envelope with explicit statuses/omissions, not an empty array or an exception that loses the source status. Existing storage-only getters should not acquire hidden source I/O.

The complete existing export mapper DTO must travel inside last_successful, the payload boundary already removed by the transient TaskEngine consumer. Adding it beside that boundary would persist source payload in task results. Projection nodes alone omit message model/weight/attachments and cannot reconstruct full history. Stable version-pinned ephemeral message/parent/group IDs need a distinct read-only capability in ChatView: it currently reads history through two paths and its edit/version/status operations assume persisted IDs. Old JNI hosts must report capability unavailable explicitly. Deleted or locally edited placeholders must not silently reappear or disappear.

This read path alone grants no model egress. The complete P4 slice must also bind source hash/selector and receiver to native R40 privacy decisions, preserve omissions and produced_by, and use reference/hash receipts instead of source text in durable chat context_trace. ActiveTask and graph-reply have separate durable payload paths; they require retention support or an explicit capability refusal before dispatch. A current-source failure may expose an independently permitted historical snapshot only as historical. These are reversible design boundaries for the next implementation, not new owner requirements or completed acceptance.


## P4a candidate — explicit local ConversationView

`Runtime::read_conversation_view` / additive `loom_read_conversation_view` composes the existing Catalog operator and full export mapper. GET `/api/conversations/:id/view` inspects metadata without source access; POST requests a local read through the existing authenticated host. Both route responses are no-store. A JSON field, source descriptor or selected node cannot supply the host grant. Storage-only getters and the schema-v4 database contract remain unchanged.

The versioned envelope contains complete/partial/unavailable status and separate per-resource current flags, native and reference rows with separate mutation capabilities, exact source/selector/version, effective read configuration, mapping status and produced_by/receipt evidence. Link resolution requires the real import journal, SourceRecord and unique conversation/message provenance. New links add a fingerprint using the existing placeholder writer; legacy links require that same unchanged writer identity. Edited, excluded, versioned or inconsistent placeholders remain stored with binding_unresolved. Native children retain their actual placeholder parent as an explicit anchor. Losing both kinds of link provenance cannot safely distinguish historical link from copy; that corrupt/unknown history remains a storage-only view and does not authorize reconstruction or source dispatch. A future journal migration may improve that diagnosis.

The full mapper lives only under last_successful, so existing transient TaskEngine stripping removes it before persistent results. New snapshots declare loom.resource_snapshot/2 and projection descriptor revision3. Historical graph-only snapshots remain stored and are not misreported as full conversations; a permitted fresh read can recompute without rewriting prior results. Defaults remain snapshot/sketch. Scanning with content_index=none validates compatible index-retention history. A transient read does not erase or certify the absence of an earlier index or snapshot; the fresh-store no-payload evidence and container-I/O limits remain as described above.

ChatView uses the same envelope for current history and branches. An explicit local-read action supports keyboard and tap; rendering or switching views does not dispatch source reads. Reference rows use the existing safe imported-message renderer and no automatic media requests. Exact native response JSON is held only in an opaque in-memory association for inspection: JavaScript-decoded fields are display projections, not a lossless reserialization of unknown numeric data. Local/native rows retain their edit/status operations. Old JNI exposes its storage-only capability explicitly.

Optional presentation.conversation_view/v1 is a separate data catalog; user.pack revision6 includes it for new profiles. Existing profiles need explicit native install_entries/CAS. Missing, excluded, disabled or proposed entries do not fall back to bootstrap; bootstrap is generated from the same canonical source and used only without a selected identity. Base UI required keys/revision are unchanged.

This candidate does not implement source-to-model context/egress: ChatView's source-history send and Expert override paths refuse dispatch until that boundary exists. Existing native chat still uses storage-only history and does not hydrate linked source content. P4b must admit transient candidates into the existing ContextEngine, bind source identity/category/receiver to actual native privacy decisions, account for transport redirects, and retain metadata-only receipts through ordinary chat, ActiveTask and method results. These are known integration gaps, not new owner requirements or a second workflow engine. Current tests and readiness are recorded in the B report; historical evidence above is not a gate for this candidate.
