# W1 native request contract

The original first-increment contract below is retained for provenance. The
addendum at the end specifies the overnight revision/callback changes.

Base: `b118c80e981c08ec6d7f9ab6aacc177979186cf2`. This is an additive consumer of
`docs/contracts/active_task_spec.schema.json`, implementing R26/R34 without
changing that frozen reference instrument or inferring statements from prose.

## Calling the existing chat API

`ChatOptions`, `loom_chat_ex` and the HTTP chat facade accept three new options:

| Option | Meaning |
|---|---|
| `active_task_spec` | Full `loom.active_task_spec/1` derived product, including statements, history event IDs and source references. |
| `active_task_bindings` | Object mapping every history event ID to `{message_id, text_sha256}`. The digest is lowercase SHA-256 of the native message text's UTF-8 bytes. |
| `active_task_history` | `replace_refinement` by default, or explicitly `append`. |

Existing callers retain their composition. Supplying a bare summary fails.
`scope.conversation_id` must identify the current existing conversation;
`scope.branch_id` is `native:active`, explicitly naming the supported native
source selection. This sentinel does not verify any imported provider branch.
Each declared history event must bind to a distinct active native message in
that conversation with exactly matching text bytes. Optional source quotes
must occur in those bytes. Include rejected assistant attempts among the
covered events when they are part of the refinement block.

The current message is a separate follow-up. It is never a source placeholder,
and appears once at the end of the request, with its existing attachment
handling. This first adapter accepts refinements already stored as native
messages; it does not extract or consolidate the in-flight user message.

A complete executable synthetic example is
`loom/tests/compat/test_chat_active_task_http.py`. It exercises the unchanged
C ABI, the real native HTTP transport and a loopback-only provider.

## Compilation and history

The compiler validates projection structure, types, timestamp shape/bounds,
local source references, supersession links/cycles, and UTF-8 byte spans.
It rebuilds `compiled_instruction` from all active/contested statements in
supplied order. Rejected/superseded statements remain in the retained product,
but are not rendered. Conditions, exceptions, contested corrections and
executor-only context are labeled using the deterministic T2 renderer format.
A structurally valid but forged incoming compiled paragraph is never executed.

`replace_refinement` removes exactly the bound messages from the history
portion of this request, without changing their database rows. It does not
infer block boundaries or completeness. `append` explicitly retains source
history alongside the compiled instruction. `include_history=false` still
keeps the instruction; memory, legacy graph and knowledge context remain
independent controls. Content in those other channels is **not** filtered by
W1. Do not claim whole-request removal of every previously rejected idea.

The derived instruction is a labeled user-role message before the current
follow-up; it is not promoted to a system instruction or presented as a
verbatim utterance. No new provider parameter is sent.

## Versioning, persistence and failure

The first accepted product for a task has version 1 and a null predecessor.
A successor must name the latest retained product in the same scope and goal
and increment its version by one. Reusing a product ID with different content
or bindings fails. Repeating the identical latest product is permitted;
reusing an older version after its successor was accepted fails. An explicit
historical replay/fork mode is not implemented in this native adapter.

Accepted products are retained in the new current user message's
`metadata.active_task`, using existing storage and schema. It contains the
supplied and compiled specs, renderer identity, bindings, native source
snapshots, history mode and `acceptance=explicit_caller_supplied`. This labels
who supplied the decision; it does not claim a separate owner-confirmation
step. This projection is not additionally registered as a knowledge-graph
Product in this increment.

Task validation and compilation precede current-message persistence. One
local Database lock spans source checking, request construction and message
creation. Locks are released before events/callbacks and HTTP. A callback that
edits a source cannot change the already compiled request or retained source
snapshot. This is process-local coordination, not a cross-process/distributed
transaction for concurrent clients of separate Database instances.

The task remains retained even when provider/authentication fails or
`trace_context=false`. Trace defaults on for task requests, and its message
array equals the array handed to transport. A compilation trace is not proof
of provider receipt. Preview `build_messages` accepts no revision and persists
nothing; `send` is the accepting consumer.

## Evidence boundaries

- No semantic extractor, model-based consolidator or model-quality claim.
  Caller-authored statements can misinterpret or omit source information.
- Native bindings verify text identity and optional quote occurrence, not
  semantic entailment or the truth of external archive locators, observation
  IDs, claim IDs, goal IDs, knowledge-run IDs or supplied provenance dates.
- Source snapshots retain text and attachment references, not attachment file
  contents. Original native source rows are left intact by the compiler.
- Native JSON integer fields require integer storage (`1.0` is rejected),
  while the Python JSON Schema reference can treat integral floats as integers.
- The receipt identifies local/native synthetic evidence separately from
  historical T1/T2 results. Sealed corpora and external models are not used.

## Overnight addendum: inherited coverage and callback acceptance

Successive products may bind only new refinement messages. The replacement
history set now includes current explicit bindings plus source messages from
the exact predecessor chain, newest first. It does not merge statement content.
`history_coverage_message_ids` and `inherited_source_messages` retain this
selection and its originating products. An unrelated task with the same goal
does not contribute source coverage. `append` and `include_history=false`
remain independent explicit choices.

An inherited source that is still active must match its accepted text snapshot
before replacement. A native edit that creates another active row in the same
version group needs an explicit verified binding in the current product or a
newer accepted ancestor. Excluded historical sources are retained but do not
block replacement. The adapter rejects invalid UTF-8 in native bound text
before persistence, preventing repaired JSON text from diverging from its hash.

Retained records are checked for recompilation agreement, source hashes,
optional quotes, product identity and an unbroken exact predecessor chain.
Present malformed active-task metadata is an error. This is consistency
checking of application records, not a cryptographic provenance proof.

During a send, a same-engine in-flight map holds the accepted canonical product
under the Database lock. Temporary callback replacement of message metadata
cannot authorize a second root for that task. The map is removed on exit; it
is not a new durable journal. Source checking is repeated after a custom
knowledge-context builder returns, before accepting the current message, since
a reentrant builder may change sources or accept a competing revision.

Synchronous message-created/on_start metadata changes are merged, canonical
active-task data is restored, and a conflicting prior value is preserved in
`loom_active_task_metadata_recovery`. Recovery precedes rejection when the
current message's text, role or attachment references changed. Such a changed
turn is not transported. The callback exception path attempts the same
retention before propagating the original exception. Missing/moved rows or a
database write failure are explicit storage boundaries, not recreated data.

The guarantee is scoped to the same ChatEngine and its synchronous accepting
callbacks. Arbitrary post-send metadata edits, separate engine/database
instances, process crashes, and later streaming callbacks need a separate
durable acceptance-store design. Original source data remains untouched by
the compiler; attachment references do not freeze external file bytes.
