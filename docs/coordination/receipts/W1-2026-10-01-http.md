## Coverage added

The original three-call C ABI smoke method remains unchanged. Three new
methods exercise exact outbound arrays and persistent records through
`loom_chat_ex` and the real native HTTP transport:

- New-only v2/v3 source bindings retain exact ancestral coverage; latest replay
  works and otherwise-valid stale products add neither calls nor rows.
- Native `loom_edit_message` creates a distinct active sibling. Replacement
  fails for the verified intended reason until the new ID, hash and quote are
  explicitly bound. The old source bytes and prior accepted snapshots remain.
- A real loopback HTTP 503 with trace disabled retains the accepted product.
  Shutdown followed by a new runtime on the same data directory preserves it;
  competing/stale versions reject and a valid successor succeeds.

The new `server.chat_active_task` CTest entry drives the public `/api/chat`
endpoint over HTTP. It checks SSE `start`/`done` versus `error`, request IDs,
actual provider payloads, v1/v2 selective coverage, and stale rejection without
a start event, provider call or current-row persistence. A trace-off v3 receives
an actual provider 503; its exact outbound array and accepted user snapshot are
verified. The subprocess is terminated and waited for, then a fresh server
reopens the same directory. Stale v2 still rejects; identical latest v3 replays.

All new fixture directories and server logs are retained for inspection. The
historical original smoke method keeps its existing temporary-fixture lifecycle.
Only synthetic data and local placeholders are used; no user sources or keys.

## Reproduced remaining boundary

The separate audit reproduced two supported-client failures without provider
calls: preserving old metadata under a nested key, or moving the accepting row
to another conversation, then reopening the runtime allows a competing v1 in
the original scope. The old data is preserved; the current ancestry reader
simply no longer discovers it. This is an observed limitation, not a fix in
this test-only increment.

See [the acceptance design and negative evidence](W1-2026-10-01-acceptance-design.md).
The proposed first fix uses the existing append-only EventLog for complete
acceptance snapshots and a SQLite transaction for user-row/event atomicity.
It distinguishes caller acceptance from owner judgement, and durable authority
from rebuildable Product projections. Upgrade/import evidence, pagination,
cross-connection races and externally owned transactions require explicit gates.
