## Actual public request

One `loom_chat_ex` / `POST /api/chat` request may carry the current `message`
and these two independent inputs:

```json
{
  "message": "Continue with the accepted task.",
  "conv_id": "the-existing-native-conversation",
  "active_task_spec": {"schema": "loom.active_task_spec/1", "...": "see exact fields below"},
  "active_task_bindings": {
    "event.1": {"message_id": "native-message-id", "text_sha256": "lowercase-sha256-of-utf8"}
  },
  "active_task_history": "replace_refinement",
  "knowledge_context": {
    "text": "Find evidence for the accepted task.",
    "run": "a-finished-knowledge-run",
    "project": "an-existing-entity-id",
    "targets": ["an-existing-entity-id"],
    "budget_tokens": 4000,
    "relation_hops": 2,
    "detail_resolution": "summary",
    "goal_type": "answer_question",
    "lang": "en"
  }
}
```

The ellipsis above is explanatory, not valid input. The exact
`active_task_spec` envelope has these required fields (only `extensions` is an
optional root field):

| Part | Exact fields and meaning |
| --- | --- |
| Identity | `schema="loom.active_task_spec/1"`, `product_ref`, `goal_id`, `scope={conversation_id,branch_id,task_id}`, integer `version`, `previous_product_ref` |
| Provenance | `known_at`, `knowledge_run`, `representation="derived_product"`, `materializer`, unique `history_event_ids`, nonempty `source_refs` |
| Statements | `statements[]` with `id`, `kind`, `status`, `text`, `source_event_ids`, `claim_ids`, `conditions`, `supersedes`, and optional `extensions` |
| Supplied rendering | `compiled_instruction={text,source_map}` is validated but never trusted; W1 regenerates it from active/contested statements |

Every history event must have exactly one binding to a distinct active native
message in the same conversation. The binding hash is over the exact UTF-8 text.
`scope.branch_id` is exactly `native:active`. The current follow-up cannot stand
in for a source event. `active_task_history` is `replace_refinement` by default
or explicitly `append`; it controls native history only.

### What W1 executes

W1 retains all statement statuses but renders only `active` and `contested`, in
caller order. Kinds are `goal`, `required_information`, `format`, `style`,
`prohibition`, `exception`, `alternative`, `open_issue` and
`executor_context`. Conditions and contested/executor qualifications are kept.
Rejected and superseded statements remain provenance and are not rendered.

The accepted snapshot is stored in current-message `metadata.active_task` and
in the append-only `chat.active_task.accepted.v1` authority event. The provider
receives ordinary messages, not the structured specification or bindings.

## Independent context controls

Current W1 accepts these strict nested `knowledge_context` fields:

| Field | Scope | Semantics |
| --- | --- | --- |
| `text` | request | Selection query; omitted/empty means the current follow-up, not the compiled task |
| `run` | request | Caller-supplied run ID whose status is not certified here; omitted/empty selects latest finished inside ContextEngine, while this normalized request field can remain empty |
| `targets`, `project` | request | Caller-supplied entity IDs, not labels and not W1 statement IDs; parsing does not prove they exist |
| `goal_type`, `lang` | request | Goal policy and rendering language |
| `relation_hops` | request | Nonnegative subject/object graph radius; default 1; zero still retains stable/project candidates and required-premise closure |
| `detail_resolution` | request | `null`, `label`, `summary`, `full` or `raw`; null uses the goal policy |
| `budget_tokens` | request | Positive item-rendering budget, default 4000; not a graph radius or whole-provider-request budget |

Radius, representation and item budget are independent. A fuller
representation can cause fewer items to fit but does not shrink the graph
radius. `raw` means the stored per-kind raw view, not an entire source file.
Existing store caps mean a requested radius is not proof of exhaustive graph
coverage.

On the integrated W2 path, `knowledge_context` additionally accepts
`plan`, `claim_targets`, `include_counter_evidence`, `candidate_channels`,
`candidate_scan_limit` and `lexical_shadow`. A plan contains `id`, opaque
`source_ref` and nonempty `theses`. Each thesis has required `id` and `text`,
with optional `targets`, `claims`, `relation_hops`, `detail_resolution`,
`require_counter_evidence` and positive `budget_weight`. Scope/detail can vary
per thesis; the total item budget and run/project/goal/channel settings remain
request-wide.

## Composition and trace

The provider message order is:

1. configured or overridden system prompt;
2. memory system section, if enabled;
3. legacy graph system section, if enabled and `context_depth != 0`;
4. W2/ContextEngine knowledge prompt as a system message, if requested;
5. active native history, with exact W1-covered source messages removed only
   in `replace_refinement` mode;
6. regenerated W1 instruction as a user message;
7. the current user message exactly once.

`include_history=false` removes step 5, not step 6. W1 does not filter memory,
legacy graph or knowledge context. Those channels can therefore mention a
rejected task alternative as evidence. That does not reactivate it as a
structured W1 instruction, but there is no semantic sandbox: the text can still
influence provider output.

The compilation trace keeps exact messages/hash and separate lanes:

- `context_trace.active_task` — W1 accepted/compiled task snapshot;
- `context_trace.knowledge_context_request` — normalized/submitted request; an
  omitted run can remain empty here even though ContextEngine selected latest
  finished internally;
- `context_trace.knowledge_context` — ContextSet and rendered prompt;
- on the integrated W2 path,
  `context_trace.knowledge_context.context_set.goal.params.plan_trace` — the
  supplied plan and per-thesis retrieval diagnostics.

`trace_context=false` suppresses returned/persisted trace but not either input's
effect. A compilation trace is not proof that a provider received the request.

## Responsibility and binding boundary

| Owner | Responsibility |
| --- | --- |
| W1 | ActiveTaskSpec validation/compilation, exact native bindings, version ancestry, durable acceptance and history replacement/append semantics |
| W2 | Retrieval plan, per-thesis scope/detail, claim/counter lookup, candidate instruments, budget allocation and explicit gaps/diagnostics |
| Integrator | Shared `ChatOptions` parser, header reconciliation, branch combination and joint regression gates |
| Caller/product UI | Explicitly author the retrieval plan and any mapping to accepted W1 statements; current code does not infer or certify that mapping |

There is currently coexistence, **not a verified W1→W2 semantic binding**:

- `plan.source_ref` is opaque caller provenance. The integration test
  deliberately accepts a bound W1 v1 beside a plan claiming v999.
- `active_task_spec.knowledge_run` does not drive or constrain
  `knowledge_context.run`; pin the latter for reproducibility.
- W1 `claim_ids` are not automatically copied into thesis `claims` and do not
  prove that the claims exist, are true, relevant or supporting.
- W1 task scope, statement conditions and output/detail requirements are not
  W2 graph scope, graph radius or evidence representation.
- Rejected/superseded alternatives are not counter-evidence. W2 `dropped`
  means selection/budget omission, not owner rejection.
- A generic follow-up such as “continue” is the default W2 query unless the
  caller supplies an explicit `knowledge_context.text` or plan.

A future bound mode should verify the exact accepted product ref/version/scope,
compiled-spec hash, knowledge run, plan identity/hash and explicit mapping from
statement IDs to theses. It must distinguish active/contested/rejected states,
fail before persistence/provider effects on mismatch, and join the trace from
statement through thesis and candidate route to selected/dropped item. That is
an additive caller/product contract plus integrator plumbing; silently
converting every W1 statement would lose semantics, especially for style,
exception, executor context and open issues.

## Remaining risk

The missing verified binding is real, not documentation debt. Until an additive
binding envelope exists, a caller can attach a stale, mismatched or unrelated
W2 plan/run to a valid accepted W1 task. Independent context can also reintroduce
rejected text in an evidence or counter-evidence channel, and W1 does not
semantically sandbox its influence on provider output. Candidate and graph caps
can truncate retrieval; counter links cover recorded relations
only; none of these mechanism tests measures semantic retrieval quality,
evidence completeness or answer correctness.
