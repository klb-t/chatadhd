# Discovery/adaptacja: niezależna bramka istniejących konsumentów

2026-10-09. Native wykonano na main `9e20f99ab27e7cd45e1892f83bf60fbe60db3de9`; dane metody C pochodzą z `b9b503f62bb8e8e00c94ab7401e1cd9579129af3`. Przeprowadzono też porównanie źródeł z B2 `384c5e1686cd3a58a7d89a8a6813a18c764f697d`. Wynik: **20 bramek, 14 PASS / 5 FAIL / 1 BLOCKED**. Cztery FAIL dotyczą jednego problemu DTO, jeden wyboru niepewnego mapowania; BLOCKED dotyczy braku powiązania agregującego kontraktu discovery z wywoływalnym konsumentem. Reprodukcja błędu nie jest sukcesem produktu.

Źródło wymagań: cytat właściciela w `../OWNER_CLARIFICATION.md`, szczególnie pkt 4–6, jako uszczegółowienie R15/R20/R21; również R41 i dokładny test R42. Nie powstaje drugi resolver ani silnik metod. Poniżej dowody i pakiety odbioru istniejących mechanizmów; nadrzędny kontrakt ma root w `../CONTRACT.md`.

Źródłowo prześledzone dodatkowe połączenia: ChatGraphExecution tworzy lokalny ProviderRegistry i ładuje jawne `provider_manifests`; embedding korzysta z Runtime.providers. Server methods opisuje host capabilities osobno od zgody i wykonania, a zapisywanie selection ma jawny request/CAS. Nie utożsamiamy odrębnych instancji istniejącej klasy z drugim silnikiem.

W badanym zakresie nie odnaleziono wspólnego workflow, który przyjmuje lokalny opis, schema, dokumentację online, strukturę i inferencję modelu, zapisuje wszystkie konkurencyjne mapowania oraz prowadzi walidację/aktywację przez jeden kontrakt. To **luka integracji ograniczona do wykazanego zakresu**, nie dowód nieistnienia dowolnej funkcji w całym repo. Są komponenty do wykorzystania: versioned method graph, parameter layers, source Observations, result-to-method Claims, explicit native capabilities, GraphPacket receipts i osobna zgoda transportu. Sam parser JSON Schema, katalog providerów lub heurystyka importera nie zamyka pełnego discovery.

## Potwierdzone problemy

**A3-DISC-001 — MethodRegistry błędnie odrzuca równoważną kolejność kluczy.** `method_registry.cpp:111–127` używa porównania `ordered_json` wyniku rzeczywistego DTO `to_json()` z wejściem. Osobne próby zmiany kolejności kluczy samego entity oraz samego claim mają **identyczne canonical bytes**, lecz każda zostaje odrzucona. Kontrola nieznanego dodatkowego pola nadal poprawnie daje jawne odrzucenie. Nie wolno naprawić tego przez usunięcie bramki lossless.

Na rzeczywistym publicznym handoff C2 surowy packet przechodzi NativeGraphStore, ale load registry daje `entity DTO is not lossless`. Diagnostyczny roundtrip przez **aktualne** `Entity/Claim/Observation::from_json().to_json()` pozwala na load. Oprócz kolejności zmienia 57 reprezentacji liczbowych: 13 `confidence` encji oraz 22 `confidence` i 22 `quality` claims z całkowitego **1** na **1.0**. Dokładne ścieżki są w receipt; brak zmiany wartości, utraty pól albo zmiany kolejności tablic. Rzeczywista bramka lossless GraphPacketStore osobno potwierdza dopuszczalność tych DTO. Po roundtrip metoda C pozostaje prawidłowo unavailable: nie deklaruje host executora. To kontrola przyczyny, **nie naprawa produktu** i nie uprawnienie do uruchomienia przechowywanego kodu.

`docs/NATIVE_GRAPH_PACKET_STORE.md:33–41` dokumentuje wcześniejszą naprawę równoważności obiektów i dokładnych liczb w store. Registry ma własne porównanie, więc tamta naprawa nie zamyka tego konsumenta. Źródła odpowiedniego store comparatora: `loom/src/kb/graph_packet_store.cpp:98–150`.

**A3-DISC-002 — heurystyka nieznanej struktury wybiera pierwsze mapowanie bez reprezentacji alternatyw.** `export_unknown.cpp:25–62` wybiera pierwszą tablicę spełniającą test message-like. `export_archive.cpp:673–700` uruchamia tę inferencję, a `export_unknown.cpp:224–242` zapisuje wynik. Dwie syntetyczne tablice `alpha`/`beta` są równie wiarygodne; przełożenie kluczy daje inną zaimportowaną wiadomość. Obie operacje zapisują rozmowę. Raw nieznanej alternatywy jest zachowane w metadata, a wynik ma `inferred=true`: to poprawne zabezpieczenia, ale nie są obiektami konkurencyjnych mapowań ani konfigurowalnym wyborem. Nie stwierdzono utraty raw bytes ani wysłania danych. Polityki wyboru, głębokości i słowniki aliasów są tutaj danymi domenowymi według testu R42, a nie gramatyką zewnętrznego standardu.

**A3-DISC-003 — luka czterech osi statusu discovery, nie potwierdzony bypass zgody.** Legacy `ProviderRegistry.status()` zwraca id/available/nazwy capabilities. Nie jest kompletnym opisem deklaracji, implementacji, dowodów i uprawnienia wymaganym nowym doprecyzowaniem. Jego dokumentowany sens `available` to obecność credentialu lub brak jego wymogu; rzeczywisty embedding consumer poprawnie dodaje readiness, live_verification, attestation i calls_authorized. Nie wolno przepisywać starego `can=true` jako dowodu wykonania ani jako potwierdzonego błędu autoryzacji. Ta bramka ma status **BLOCKED / unbound_new_requirement**, a finding kategorię **niepewne / integration contract gap**. Nie wymaga arbitralnych nazw nowych pól; równoważne, wyjaśnialne rozróżnienie w istniejących facets jest dopuszczalne. Pierwotne shape assertion zostało odrzucone w review oracle; wcześniejszy receipt zachowano i nie liczymy go jako błędu produktu.

## Odbiór dla B i granice pokrycia

Pakiety w `HANDOFF_B.md` i `backlog.json`: poprawić porównanie DTO bez osłabiania walidacji, reprezentować alternatywne mapowania i jawną politykę wyboru przez istniejące metody, rozszerzyć agregację capability status bez utożsamiania zgody z credentialem. Automatyczna walidacja i aktywacja mogą być strategiami jawnej polityki; raport nie narzuca ręcznego potwierdzenia każdego kroku i nie nadaje discovery nowych uprawnień.

`coverage.json` podaje jawny mianownik plików badanego podsystemu, konkretne prześledzone zakresy oraz hashe na main/B2/C2. Wszystkie weryfikowane pliki produkcyjne poza bootstrapem Runtime są identyczne na tych przypięciach; porównanie B2 nie udaje niezależnego wykonania całego B2. Nie powtarzano badań korpusu C, nie testowano jakości modelowej inferencji, dostępu online, pełnego UI, urządzeń ani power loss. Pozostałe zakresy są wymienione w coverage i kontrakcie roota.

Wywołania płatne: **0**; sieciowe: **0**. Jeden request embedding wykonał wyłącznie rzeczywisty ScriptedTransport, który nie ma backendu socket. Workers wyłączone. Syntetyczne ZIP-y służyły wyłącznie sprawdzeniu niejednoznaczności; nie dublują pionowego testu ZIP/ref/import innego audytora. Nie zmieniono kodu produktu, wspólnych schematów ani cudzych gałęzi.

Punkt wznowienia: uruchomić niezmieniony `discovery/run.py` przeciw native buildowi poprawki i dokładnemu SHA, zachować PASS nieznanego pola/zgody/unavailable. Po przyjęciu kontraktu discovery dodać jego adapter do tych samych bramek; nie zastępować rzeczywistego konsumenta testową implementacją.
