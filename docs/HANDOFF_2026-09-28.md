## 5. Directions for you (large, open-ended — explore, branch, measure)

### 5.1 The central research programme: methods to analyse structure and meaning

This is, in the owner's words, one of the most important parts of the system,
and it needs testing, modification, iteration and branching exploration paths.
Build a **palette** of methods, each measurable on the benchmarks, and let them
compete and combine. Directions (not prescriptions):

- **A representation of the structure of an argument / a thought / the meaning
  of words**, usable before the full epistemic model (LEM) exists: define it
  from several perspectives and compare them mathematically — e.g. geometric
  (embedding spaces, subspaces, projections, cones for generality),
  topological (persistent homology of concept graphs, shape of argument
  graphs), graph-theoretic (motifs, homomorphisms between argument graphs),
  logical/algebraic (typed claims, lattices of generalisation, category-like
  compositions of morphisms), information-theoretic (compression: state +
  generators + exceptions).
- **Levels of generalisation**: for every analysed statement or topic compute
  its generalisations at several levels (what category it belongs to, what it
  is an example of, which relation it instantiates, its structure), and
  measure **universality** of a pattern (how many domains/contexts it recurs
  in) and **specificity** (how much structure it carries) as *separate*
  dimensions — the owner stresses specificity is not simply the inverse of
  universality.
- **Recurrence across time and topics**: when was a structurally similar thing
  last discussed, especially in a different topic; surface **unstated
  conclusions** (inferences the owner's own premises imply but were never
  said), with Expected Properties and evidence.
- **Far associations and bridges**: multi-topic brainstorms (e.g. philosophy ↔
  physics ↔ mathematics ↔ AI alignment) are the best test material; detect,
  rank and explain cross-domain bridges.
- **Pattern mining and abstraction**: repeated patterns → candidate
  templates/operators/principles → evaluation → promotion (MEGA MASTER §2.H).
  Operator mining from decision sequences; template induction of project kinds
  and artifact types; morphism discovery between kinds.
- **Multimodal embeddings** (e.g. Google multimodal embedding models) behind
  the `embed` capability: text, images, audio, video in one space; compare
  with TF-IDF and with structural methods; always record which method produced
  a claim.
- **Benchmarks** decide: temporal holdout on the owner's real history (the
  generator must predict later decisions at the level of solution class),
  synthetic corpora (write more, with different fictional authors and domains —
  never imitate the real owner), calibration (ECE), false certainty, context
  efficiency. Keep a leaderboard of methods.

### 5.2 Complete interpretation of provider exports

- Interpret OpenAI and Anthropic exports fully and losslessly (every file and
  field; current and archival export formats). Where the structure is unknown,
  look it up on the internet (documentation, community parsers) and, failing
  that, infer it from names and relations — marked as inferred.
- Link attachments, files, images, audio, canvases/artifacts, projects,
  memories and custom instructions to the conversations and messages they
  belong to; model them in the graph (R14, R15, R17).
- Cross-provider memory isomorphism: one memory abstraction with morphisms from
  ChatGPT memories, Claude memories/projects, and future providers.

### 5.3 Everything in the graph, with rich edges

User profile, preferences, project abstractions (kinds, roles, morphisms),
memories, connectors/providers, settings, the UI's own layouts — all as
entities; edges typed, qualified, time-scoped, assessed, with provenance (R15).

### 5.4 Interface: maximum functionality, never either/or

- Owner's principle: the interface gives access to, and visualises in every
  possible way, all relevant data, connections and controls; the user decides.
  **Never force a choice between views**: the user may open five coordinated
  graph views at once (linked selection, brushing, shared focus), plus lists,
  tables, timelines, dossiers — all synchronised, for navigating a
  multi-dimensional space (perspective, alpha, depth, many sliders for context
  dimensions) (R16).
- **Provider-inspired interface profiles as data** (R17): after importing
  exports, the owner can choose to see Anthropic conversations as in the Claude
  app and OpenAI conversations as in the ChatGPT app — including archival app
  versions — with functionality replicated as far as possible, own graphics,
  similar logic (study existing open-source clones); interface profiles are
  data, not code. Later: survey other apps and map (not clone) their interface
  logic within copyright limits.
- The owner's mockup is the reference for the workbench (dockable/floating
  panels, project structure with dimmed inferable nodes, active context window,
  artifact views for video/music, execution environment).

### 5.5 Scan the whole codebase for generalisations and options

Apply the owner's test everywhere: "if a new case needs a new code branch,
check whether it should be a data value". Find hard-coded choices that should
be owner options, duplicated structures that should be one abstraction, enums
that should be capability data, UI decisions that should be preferences. Every
option the owner could want should be an option (with sensible defaults).

### 5.6 Privacy and threat model (R19)

Privacy profile for every provider/connector/storage/device path; attacker
catalogue with required effort (API compromise, legal compulsion, device
spyware of the Pegasus class, physical/acoustic/optical side channels); what
Loom controls, cannot control, and cannot know; a "paranoid" mode showing the
full risk map and routing accordingly. Comprehensive model, details in the
background of the UI.

### 5.7 Second project: the legal case (R9)

## 6. Working rules that proved necessary

- Keep one meaning per term (update the conceptual model first).
- Commit and push small increments; long runs get interrupted.
- Python↔C++ compat invariant for core tables (`schema_version` 4); new state
  only in `loom_*` tables.
- Deterministic outputs (content ids, ordered reassembly); inference ≠ fact;
  owner judgements always win; honest degradation when a capability is
  missing.
- Worktree agents start from `main` by default — merge the working branch first.
